# AIF 研究第二轮 — 对象数组行内化 & `should_use_aif` 预估器

- Generated: 2026-11-08 13:06:53
- Tokenizer: `cl100k_base` (tiktoken 0.14.0)
- 规模：参数扫描 200 条/组；V8 真实数据 1000 条/组
- **只读研究**：不改 AIF/0.9 格式、encoder、decoder、benchmark 数据或任何测试
- **所有变体均为 counterfactual，仅用于 token 计数**：不是已实现语法、未做 round-trip、不得称为 AIF 特性

## 结论先行

1. **对象数组行内化有效，但不通用**：57 组可折叠数据中，50 组省 token、3 组反而更费、4 组持平；平均每组变化 +2,810 tokens （范围 -40 ～ +27,518）。
   `\n` 在 BPE 里常与相邻字符合并成单 token，所以「省换行」不必然省 token —— 与第一轮 `-N` 合并缺失行的反直觉结论同源。

2. **真正的大头是 schema 行重复，不是换行**：`@objects` 的 schema 行在每条记录里都重写一次。把它提到全局只声明一次（hoist），57 组平均每组省 +3,628 tokens，中位数 +2,928；最大 +16,983。这比行内化稳定得多。
   hoist + 行内化组合上限：平均每组 +6,439 tokens。

3. **V8 真实对象数组场景的改善幅度**（Δ 为相对各自基线的 token 变化）：
   - V8 08 Array of Objects: JSON 41,003 / AIF-S 37,013 (+9.73%)；inline +3,000、pipe +0、hoist +7,992、all +10,992 tokens
   - V8 10 Multiple Tool Calls: JSON 69,002 / AIF-S 62,015 (+10.13%)；inline +5,000、pipe +1、hoist +16,983、all +21,983 tokens
   - V8 17 Mixed realistic: JSON 78,002 / AIF-S 70,031 (+10.22%)；inline +4,000、pipe +0、hoist +15,984、all +19,984 tokens
   `pipe` 在 Text Mode 基线上几乎零收益：`|` 自身在 BPE 里也要占 token，替换掉换行（常与相邻字符合并成单 token）省不到东西。**行内化只在 Structured Mode 下有意义**。

4. **兼容性成本不能忽略**：空格方案在 Text Mode 下会歧义 —— 全部 57 组数据的值内空格共 4,000 处；`|` 方案需新增「值内 `|` 必须转义」规则（本次数据内 `|` 出现 0 处，所以测出的收益是**上界**）。另有 0 个含数组类型字段的 `@objects` 块无法用定长方案折叠。
   任何一项都要求同时改 encoder、两套 decoder、规范、双实现一致性测试与 fuzz —— 而 0.9 已定稿。

5. **预估器研究得到的是否定结论：近似判据不足以驱动决策**。
   线性模型在合成留出集 80 组上二分类准确率 88.8%、MAE 7.42pp；在**从未参与拟合**的 V8 17 类上准确率 94.1%，但 MAE 高达 21.78pp —— 预测 +30～+57%、实际仅 +0～+54%，系统性高估（合成训练集的结构比真实数据更有利于 AIF）。
   **关键**：V8 上模型误判代价 11,019 tokens，与「总是用 AIF Text Mode」的 11,019 **完全相同** —— 两者都只错 `07 Array`，训练出来的模型没有增量价值。来自第一轮结论的可解释规则在 V8 上代价 0（看似达到 Oracle），**但在独立合成留出集上代价高达 50,083 tokens**（线性模型仅 448）—— 两者在不同留出集上互有胜负，谁都不能泛化；规则在 V8 上的好表现只是 `07 Array` 的 `array_density=2.30` 恰好跨过阈值 2.0。
   因此 `should_use_aif(exact=True)` 是唯一可靠路径：真编码、真计数、验证 round-trip、100% 准确；代价是编码成本已付，适合批量/缓存决策，不是零成本预估。

6. **建议：两项 counterfactual 都不进 0.9**。行内化收益不稳定且需破坏兼容性；schema hoisting 收益稳定但属格式级变更，值得作为 **AIF/1.0 候选扩展单独立项**。预估器保留为研究工具，但**不把近似模式包装成可靠组件**：`exact=False` 的结果一律带 `reliable=False` 与警告，文档推荐 `exact=True`。

## Part A — 对象数组还能不能更省

### 方法

当前 `@objects` 块布局（每个字段占一行，schema 每条记录重写一次）：

```
@objects
name:s arguments.query:s arguments.limit:i result.success?:b
3
web_search
AI\stechnology
10
true
...
```

四个 counterfactual（`s` = Structured 文本，`t` = Text Mode 文本）：

| 变体 | 定义 | 前提 |
|---|---|---|
| `inline` | 每个 object 的所有 slot 用空格拼成一行，基于 `s` | 值已用 `\s` 转义空格 |
| `pipe` | 每个 object 用 `\|` 拼成一行，基于 `t` | 值内 `\|` 需要新转义规则 |
| `hoist` | 重复的 schema 行只保留第一次（假设全局 schema 注册表） | 需全局 schema 语义 |
| `all` | `hoist` + `inline` 组合上限 | 两者前提叠加 |

`Δ` = **变体所基于的基线** tokens − 变体 tokens（`inline` / `hoist` / `all` 基于 AIF-S，`pipe` 基于 AIF-T），**正数表示省了**；这样不会把 Text Mode 自身的收益错算到行内化头上。含数组类型字段的块因行数不固定，标 `N/A` 并原样保留，不估算。

### 歧义与兼容性成本

- 值内空格总数：4,000（空格分隔方案在 Text Mode 下不可用）
- 值内 `\|` 总数：0（`\|` 方案需要新转义规则；当前数据几乎不出现，所以 `pipe` 是无转义成本的上界）
- 含数组类型字段、无法定长折叠的 `@objects` 块：0 个
- 三个变体都需要改动：encoder + Python/JS 两套 decoder + 规范 + 双实现一致性 + fuzz
- 本报告**没有**实现这些变体，也没有对它们做 round-trip 验证

**判断**：`inline` 收益在 k 与值类型间来回翻转，不是可靠优化；`hoist` 方向稳定但需要全局 schema 语义，属于格式级变更。两者都应留到 AIF/1.0 候选扩展，不塞进已定稿并通过 fuzz 的 0.9。

## Part B — `should_use_aif` 预估器

### 方法

- 实现：`research/predictor.py`，**独立研究工具**，不被任何测试 / benchmark / 核心包导入
- 训练集：**仅合成参数扫描** 320 组（跳过 0 组不支持的结构），固定 seed `20261108`；V8 17 类数据**完全不参与拟合**
- 留出集：独立合成 80 组（seed `777001`，跳过 0 组） + V8 17 类真实数据（n=1000）
- 两个线性回归（Structured / Text），标签是真实 `cl100k_base` reduction
- 10 个特征，全部为纯结构统计，**不调用 AIF encoder、不调用 tokenizer**：
  `key_share`、`long_text_share`、`space_share`、`array_density`、`obj_array_density`、`log_records`、`missing_share`、`log_fields`、`avg_key_len`、`log_value_len`
- 决策：取 `max(预测S, 预测T, 0)`，输出 `json` / `aif-s` / `aif-t` 三选一
- 对照组：可解释粗规则（阈值来自**第一轮已发表结论**，不用 V8 标签拟合）、「总是 JSON / 总是 AIF-S / 总是 AIF-T」三条基线、`exact=True` 真编码路径、以及理论最优 Oracle

### 为什么近似判据分不开：聚合特征冲突表

下表是本研究最重要的证伪证据。`arr` = `log1p(每记录 scalar 数组元素数)`，`ratio` = `arr / key_share`（数组开销相对键名收益），`best` = 两种 AIF 模式下实际最优 reduction（0 表示应保留 JSON）。

| Case | key_share | arr | ratio | 实际 best | 应选 | 粗规则 |
|---|---:|---:|---:|---:|---|---|
| 短数组+短键 (200) | 0.68 | 1.39 | 2.03 | +0.00% | json | aif-s |
| 长键名短数组 (200) | 0.80 | 1.39 | 1.73 | +0.00% | json | aif-s |
| 单元素数组 (200) | 0.76 | 0.69 | 0.91 | +0.00% | json | aif-s |
| 10 元素数组 (200) | 0.37 | 2.40 | 6.42 | +0.00% | json | json |
| V8 07 Array | 0.43 | 2.30 | 5.31 | +0.00% | json | json |
| V8 11 Agent State | 0.67 | 1.10 | 1.63 | +25.52% | aif | aif-s |
| V8 12 Memory | 0.66 | 1.39 | 2.11 | +24.93% | aif | aif-s |

`arr≈1.39` 这一档同时存在 **best=0%（该用 JSON）** 与 **best≈+25%（AIF 明显更省）** 的数据；`ratio` 在 2.03（该用 JSON）与 2.11（AIF 省 24.93%）处也几乎重合。根因是收益取决于 **BPE 在 token 级如何切分**，而几个聚合特征丢掉了「数组元素与其他嵌套键名重复量的相对结构」。
要可靠判定，只能真的编码并计数 —— 这正是 `exact=True` 做的事。

### 局限（不隐藏）

- 模型只在 `cl100k_base` 上校准。第一轮已证明 `p50k_base` / `r50k_base` 会把 `17 Mixed realistic` 从正翻成负，换 tokenizer 必须重新拟合。
- 线性模型对长文本的非线性收益衰减拟合有限，`exact=True` 才是可靠答案。
- 合成训练集与真实数据分布不同；V8 上的 MAE 才是应当参考的数字。
- 预估器不做 round-trip 检查；`exact=True` 会做，并附三种 token 数。
- 特征是纯结构统计近似（`missing_share` 按各层字典键并集估算），不等价于真实 AIF slot 计数；对训练分布外的极深嵌套或混合编码结构泛化有限。
- 粗规则阈值 `array_density >= 2.0` 是人工设定，虽未用 V8 标签拟合，但其数值选择受第一轮扫描与本报告特征观察影响，属于**弱验证**；V8 只有 17 类数据，任何「达到 Oracle」的说法都只在本书数据源内成立。
- 训练集全部为合成数据，其 `key_share` 普遍高于真实混合数据，是系统性高估的主因；扩充真实分布训练样本可能改善 MAE，但本研究没有做（避免用过拟合换取好看的数字）。
- 本轮**没有**为提高准确率而修改任何 benchmark 数据集，也没有删掉决策失误条目。

### 用法

```python
import sys; sys.path.insert(0, 'AIF/research')
from predictor import should_use_aif

d = should_use_aif(data, exact=True)   # ← 推荐：真编码 + 真计数 + round-trip
print(d['recommended_mode'], d['reduction_pct'], d['reliable'])

d = should_use_aif(data)               # 粗估：reliable=False，带 warning
d = should_use_aif(data, method='rule')  # 可解释粗规则：同样不可靠
```
