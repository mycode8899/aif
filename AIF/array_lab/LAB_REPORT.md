## 结论先行

1. **在预先定义的对象数组目标工作负载上，`row`、`column`、`hybrid`达到「稳定优于 JSON」门槛**（≥80% 数据点为正、每个 seed 均值为正、round-trip 全 PASS；48 个数据点 × 3 个独立 seed）。**但这不等于「Array 问题整体解决」**：这是 AIF 已知优势场景，同场基准 `aif09-s`/`aif09-t` 本身也通过判定（45/48 正例），偏袒问题见 §2.4；标量数组仍是未解决的负例。

2. **真正的增量是相对 0.9，不是相对 JSON**：实验方案平均 reduction +43.04% ～ +43.78%，vs 0.9-S +26.97%；`row` 平均每组比 0.9 少 7,618 tokens（+16.81 pp，48/48 组更优）。

3. **小型数组负担被消除了**：`row` k*=1；`column` k*=1；`hybrid` k*=1；`aif09-s` k*=2；`aif09-t` k*=2（f=5）。0.9-S 在 k=1 是 -24.70%、要到 k≥2 才转正；三个实验方案 k=1 即为正（Row +28.52%）—— 原因是 schema 全局只声明一次、且不再为每条记录重复写数组键名。

4. **错误恢复抓到 0.9 的一个真实缺陷**：24 次损坏注入中静默损坏 2 次，**全部来自现有 0.9**（截断到 `@record` 边界会静默少一条记录，因 0.9 没有记录总数声明）；三个实验 codec 因 `@//groups/` 声明为 0 次静默损坏。但所有方案都是 fail-fast，均不支持局部恢复，这仍是共同弱点。

5. **Hybrid 的判定以绝对总 token 为准**（平均 reduction 在百分比口径上可能给出相反排序，因为各数据点 JSON 基数不同）：阈值只在与评估集不相交的校准集拟合（{"k": 8, "f": 2, "L": 8, "M": 0.15}）。目标集总 tokens —— Hybrid 1,986,218、总是 Row 1,987,219、总是 Column 1,990,658。**Hybrid 比平凡基线少 1,001 tokens，但只占 0.050%**，却要多一层模式切换语法与最高的编码耗时；**结论是不值得为它引入新语法**。（平均 reduction：Hybrid +43.73% vs Row +43.78%。）

6. **不把「所有 Array 场景都优于 JSON」当目标**：标量数组 V8 `07 Array` 仍是 -38.25%（0.9 Structured，本 Lab N=200），三个实验方案明确不覆盖；长文本、高缺失率、单对象组等劣势数据在 §4 全部保留。

## 1. 实验设计（测量前冻结）

### 1.1 公平性约束

| 约束 | 落实方式 |
|---|---|
| 相同数据 | 同一 Python 对象依次交给 6 种编码，不重新生成 |
| 相同 tokenizer | `cl100k_base`，全部方案用同一个 `tokens()` |
| 相同 JSON 序列化 | `json.dumps(..., ensure_ascii=False, separators=(',',':'))`，与 V8 逐字相同（运行时断言一致） |
| 可解码 | 每个候选都真解码并与原对象比较；不可解码不算候选 |
| 不事后挑数据 | 目标工作负载、网格、seed、判定阈值全部写在 `lab_spec.py`，实验脚本只读不写 |

- 序列化规则自检：与 `benchmarks/benchmark_v8.json_text` **完全一致**

### 1.2 预先定义的目标工作负载（唯一用于「稳定优于 JSON」判定）

```text
结构      : [{"<array>" : [ 扁平标量对象, ... ]}, ...]   组数 N = 200
字段数 f  : (3, 5, 8)
每组对象数 k: (2, 5, 10, 20, 50)   另含变长组 k_i ∈ [1,10]
随机 seed : (101, 202, 303)   字段名短英文，值短标量，缺失率 6% / null 3%
判定门槛  : ≥80% 的数据点 reduction > 0，且每个 seed 的平均 reduction > 0%，且 round-trip 全 PASS
```

**范围外（如实列出，不隐藏）**：标量数组（V8 `07 Array`）、嵌套数组、
以长自由文本为主的载荷。行/列/混合三方案**不覆盖**这些结构；
它们只作为参照与对抗数据出现，报告里保留其负 reduction。

### 1.3 三种实验编码

三者共用完全相同的转义规则、schema 声明、组数声明与 `@//data/` 块，
**唯一差别是数据矩阵的转置**，因此差异只来自 BPE 对值分组方式的敏感性：

| 方案 | 数据布局 | 每个 `@//data/` 块 |
|---|---|---|
| A Row | 一个对象一行 | k 行 × f 列 |
| B Column | 一个字段一行 | f 行 × k 列 |
| C Hybrid | 由确定性规则在 A/B 中选一 | 同上，块头写 `@//mode/` |

列式规则（对应你点名的四项）：

| 情形 | 编码 | 说明 |
|---|---|---|
| 值内逗号 | `\,` | 切分只认未转义逗号 |
| 反斜杠 / 换行 / 控制字符 | `\\` `\n` `\r` `\t` `\uXXXX` | 与 0.9 一致 |
| 空字符串 | `\e` | 与「字段缺失」区分 |
| 字段缺失 | `-` | 固定占一个 cell，游标不漂移 |
| null | `@null` | 字面量 `@null` 编码为 `\@null` |
| `@` / `-` 开头字符串 | `\@` / `\-` | 避免与标记冲突 |
| 不同长度数组 | 每块首行写 `<k>` + 全文 `@//groups/ <N>` | 变长可解码；组数声明用于检测「截断到块边界」的静默丢数据 |

Hybrid 是**确定性纯函数**，不接受人工挑选：

```python
mode = 'column' if (k_bar >= T.k and f >= T.f and L <= T.L and M <= T.M) else 'row'
```

4 个阈值只在**校准集**上网格拟合（12 组，f∈(2, 4, 7)、k∈(3, 7, 15, 30)、seed 909），
其 (f,k) 组合与目标集 f∈(3, 5, 8)、k∈(2, 5, 10, 20, 50) **完全不相交**。
拟合结果：`{"k": 8, "f": 2, "L": 8, "M": 0.15}`，校准集总 tokens 339,253。

### 2.4 目标工作负载是否偏袒 AIF？（必须正面回答）

**是，偏袒。** 目标工作负载选的是对象数组，这是 AIF **已知的优势场景**；
0.9 Structured 本身在该集合就有 45/48 个正例。
所以本 Lab 的「稳定优于 JSON」**不能**解读成「Array 问题整体解决」。

选它的理由（测量前写死在 `lab_spec.py`，不是看到结果后挑的）：
你给出的 `users[]:object @//columns/` 草案就是对象数组；
第二轮研究量化过 `@objects` 的 schema 逐记录重复是最大浪费。

**未解决的部分，不打折扣列出**：

- 标量数组 V8 `07 Array`：0.9 Structured -38.25%（本 Lab N=200 实测；V8 全量 N=1000 为 −37.99%）。三个实验方案**明确不覆盖**该结构。
- 第一轮研究已把标量数组行内化作为 counterfactual 测过：对短字符串数组有效，对整数数组零收益，不是通用解法。

因此本轮能诚实主张的是：

> **在预先定义的对象数组工作负载上，三个实验方案都稳定优于 JSON（+43.04% ～ +43.78%，3 个独立 seed），且相对 0.9 有约 +16.81 pp 的增量；同时把 k=1 的小型数组从 0.9 的负例翻成正例。标量数组仍是未解决的劣势场景，不宣称 Array 问题整体解决。**

另外，k 较小时 Row 优于 Column、k 增大后 Column 反超（见 §3），
说明「谁更好」取决于 BPE 切分与矩阵形状，不是固定结论。

## 7. 建议

- **AIF/0.9 保持定稿不动**：本 Lab 是独立实验目录，header 用 `AIF/1.0-alpha`，没有修改 0.9 的 encoder/decoder、规范、benchmark 数据或测试。
- **建议把 `row`/`column`/`hybrid` 列为 AIF/1.0 候选扩展单独立项**；立项前需补齐嵌套对象、标量数组、跨 tokenizer 与第三方实现验证。
- **字段名只出现一次（全局 schema）+ 组数声明**是本轮可复用的设计结论：前者消除结构重复，后者让「截断到块边界」不再静默丢数据，只多一行开销。
- **建议给 0.9 也补一条记录总数声明**（哪怕只是可选扩展）：§6 实测它在 `@record` 边界截断时会静默少一条记录，这是现有实现的真实缺陷，与 token 效率无关，属于可靠性问题。
- **列式不一定是赢家**：Row 与 Column 只是转置，差别来自 BPE 切分；具体选谁应由确定性规则 + 实测决定，不应凭直觉。
- **下一步的硬门槛仍然是第三方独立实现**（见 `conformance/`），而不是再写一个我们自己版本的编码器。

## 8. 局限

- 只测了 1 个 tokenizer（`cl100k_base`）和 1 种语言（Python 实现）；第一轮研究已证明跨 tokenizer 方向一致但幅度会变，本 Lab 未重复该扫描。
- 实验 codec 只支持**扁平标量对象**，对象内嵌对象/数组会明确报错，不是静默产出错误数据。
- 字段名不允许含空格、逗号、`:`、`@` 等语法字符。
- 耗时数字受本机 CPU 与 Python 版本影响，只作相对量级参照。
- 目标工作负载是**人为定义的合成数据**，不是真实生产流量；结论只在它的参数范围内成立。
- `AIF/1.0-alpha` 是实验 header，与 `AIF/0.9` 不兼容，两者不可混用同一 decoder。
